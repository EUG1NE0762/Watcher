Watcher never spoofs a user agent or ignores robots.txt. Sources it can't crawl are covered through the moderator **verified import** (CSV/JSON) or by agreement with the publisher.

## Pipeline (daily, `ingest` Edge Function)

1. **Fetch:** for each enabled source feed, check robots.txt first, keep at least 1.5 s between requests to the same host, and time out after 20 s. Only items from the last `INGEST_MAX_AGE_DAYS` (default 14) are considered.
2. **Pre-filter:** a keyword filter (police, robbery, drugs, DEC, arrested…) so the model only sees relevant stories, capped at `INGEST_MAX_ITEMS` per run.
3. **Extract:** the open-weight model returns `{incidents: [...]}` JSON (category, substance, location text, city, date, severity 1–5, a one-sentence summary with no names). The result is validated with zod; invalid output is dropped.
4. **Map to an area:** fuzzy n-gram match against area names and aliases. If that fails, a Nominatim geocode followed by point-in-polygon. If the story names a covered city but no area matches, the record is stored as **pending** for a moderator. Stories outside covered cities are skipped.
5. **Verify** (`assessCandidate` in [`packages/scoring/src/verification.ts`](../packages/scoring/src/verification.ts)):
   - **Reject** when: the URL is missing or invalid; the URL's domain doesn't match a registered source (including a claimed source on the wrong domain); the published date is missing or in the future; the summary is empty; the source is the demo source; or the source is corroboration-only and nothing corroborates it.
   - **Duplicate** when the text hash is identical, or the same source reports the same area, category and ±3 days with a similar summary.
   - **Corroborate** when the same incident comes from a *different* source. The source is attached and the confidence recomputed.
   - **Accept:** `verified` when the area is mapped and confidence is medium or high, otherwise `pending`.
6. **Recompute** scores for affected areas, then push alerts to people who saved those areas.

The `recompute-scores` job also runs daily over every area, so recency decay applies even on days with no new incidents.

## Confidence

| Level | Rule | Score weight |
|---|---|---|
| High | Any official source, or 2+ independent credible outlets (credibility ≥ 0.6) | 1.0 |
| Medium | Exactly one credible outlet | 0.7 |
| Low | Only weak sources. Held as `pending` until a moderator acts | 0.4 |

## Manual verified import

The admin screen (moderators only) accepts:

- **Incidents** in CSV or JSON, with columns `area,category,severity,substance,occurred_at,published_date,source,source_url,summary`. Every row goes through the same verification gate, so rows with untraceable sources are rejected.
- **Official statistics**, with columns `area,city,category,period_start,period_end,count,source_url,published_date,notes`. These are stored in `official_stats` and shown on the area screen. They are context, not scored incidents.

## Community reports

Community reports are stored in `community_reports` and shown on the area screen as **Unverified** (or **Moderator approved**). They are never read by the scoring engine. A report is only auto-marked as corroborated when a verified, credible, non-demo incident of a compatible type exists in the same area within ±7 days, and in that case it's the *incident* that counts, not the report.

## Demo data

`supabase/seed.sql` contains illustrative incidents generated by [`packages/scoring/src/demo.ts`](../packages/scoring/src/demo.ts). They have `is_demo = true`, are attributed to the fictional source `demo` ("Watcher Demo Dataset (illustrative, not real)") with `example.org` URLs, and their summaries start with `[DEMO]`. The UI shows a **Demo data** badge on any rating that uses them. To remove them:

```sql
delete from public.incidents where is_demo;
delete from public.sources where id = 'demo';
```
